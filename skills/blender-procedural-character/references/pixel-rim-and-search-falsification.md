# 像素段搜索收口：特效类指标的证伪与再判定（T20 实测）

本文件补 `references/pixel-segment-search.md` 的**结论层**：那一份讲「怎么跑像素段搜索」，
这一份讲「跑完之后怎么判断某个视觉指标到底存不存在」。2026-11-01 在
`Tools/人物建模` 收口像素段时，一套 24 次评估的搜索**推翻了三轮人工实验的结论**，
代价是发现旧指标是假达标。

## 1. 特效类指标必须先证伪，再谈达标（本项目最贵的一课）

旧口径（绝对亮度找亮带）在 `rim_energy=80W` 时报 `rim_skirt_p50=10.0 / rim_hair_p50=11.0px`，
看着"轮廓光达标"。**把 rim 灯关掉（`rim_energy=0`）后仍然报 10.0/11.0，逐位相同** ——
于是之前的"可达"结论作废：那 10~11px 量的是裙褶/头发**自身的 toon 色阶亮面**，
toon 三档把暗→中→亮渲染成 ≥8 的亮度台阶，任何绝对阈值都会把它们算成"亮带"。

反向的坑同样存在：同一条目此前判过"不可达 0px"（C4/D 阶段），也是绝对亮度口径在另一个
方向上失灵。**同一个口径能同时产出"假达标"和"假不达标"，所以口径本身必须做对照实验。**

判定手法（可复现、不依赖看图）：

| 实验 | 期望 | 说明 |
|---|---|---|
| 贡献源关掉（rim=0） | 指标必须**严格为 0** | 不为 0 就说明量的是别的东西 |
| 贡献源拉满（rim=400） | 指标必须上升 | 不动就说明口径钝 |
| 换方位（back / back_left / left / back_right） | 亮带必须跟着灯换到那一侧 | 左右侧 100% 互斥是"真轮廓光"的指纹 |

实测：`rim=0` → 0.00（n=0）；`rim=80` → 3.00；`rim=80 + back_right` → 10.00。
旧口径在 rim=0 时给 11.0，**新口径给 0.0** —— 这就是对照实验的全部价值。

## 2. 差分口径的写法（on/off 两张图逐像素亮度差）

```
d = lum(rim ON) - lum(rim OFF)          # 同机位、同几何、同材质、其它灯不变
跳过描边壳（lum_off < 70 连续段，最多 12px）
base 取关灯图 [k+6, k+20] 中位；base > 150 的行跳过（只量深色主体）
向内扫 14px 找第一段连续 d >= 8，且其后必须回落到 8 以下（先升后降）
宽度 = 该连续段像素数
```

要点：
- **前景掩码用关灯图**（特效灯不应改变 silhouette），否则边界会随灯强漂移。
- 色阶亮面在两张图里逐位相同 → 差值恒 0，天然被排除，不需要额外的"暗主体"阈值兜底
  （但保留它可挡皮肤/白衬衫的 bloom）。
- 渲染确定性要先验：本项目 EEVEE 48 samples 下，同参数两次渲染的 skin/outline 指标逐位相同，
  差分才有意义。**先确认确定性再建差分**，否则会把渲染噪声当成信号。
- 加 2 张渲染的成本：单次评估从 3 张变 5 张，实测 2.3~2.5s → 3.4~3.5s，24 次预算只多 20s。

## 3. p50 必须配覆盖率与位置分布，否则会夸大 10 倍

差分口径给出 `rim_band_px=10.0`（头发区）。只看这个数会以为"整圈轮廓光 10px"。
把行分布打出来才发现：

- 46 个被点亮的行**全部**落在 z 1.6025~1.6198（颅顶下方 17mm 的高度带），占该区域
  轮廓行数 46/511 = **9.0%**；
- 裙区 33 行、宽仅 2px，占 33/185 = 17.8%；
- `rim=0` 与 `rim=80` 的**被点亮行全都在朝向 rim 灯的那一侧**（back_left: L=11/R=0；
  back_right: L=0/R=46）。

**判定要分三层写**：可达（有 ≥2px 的实测）/ 是否整圈连续（覆盖率）/ 方位是否物理一致。
本项目最终判「**局部可达、非整圈连续**」—— 任务书给的"若 ≤1px 就写不可达"这个二选一
不成立，硬套会漏掉"局部有、整圈无"这个真实状态。

## 4. 枚举维的全枚举必须落在 baseline 上，不能落在 top-1 点上

前一位的实现是"在 top-1 点上把枚举维全扫一遍"。这**不是**全枚举，而是"在最优点附近
枚举" —— 而最优点本身已经偏离了默认值，于是永远发现不了「baseline 换一个方位」这种
零代价改进。

正确做法（本项目实测有效）：Halton 之后，对 `space_pixel.defaults()` 做 4 方位全扫，
再把枚举维从 `DIM_ORDER`（±1 坐标下降）里拿掉。

结果：`back_right` 与 `back_left` 的 score **完全相同（都 4e-06）**，但 rim 3px vs 10px，
皮肤四项**逐位相同**（195.02/26.82/32.00/4.77）、描边同为 3px。这是全项目唯一的
"免费改进"，只有 baseline 全枚举才找得到。

## 5. score 打平必须有 tie-break，否则严格 `<` 会永远停在 baseline

```python
better = (s < cur["score"] - 1e-9
          or (abs(s - cur["score"]) <= 1e-9
              and (m.get("rim_band_px") or 0.0) > (cur["metrics"].get("rim_band_px") or 0.0)))
```

为什么必须写进代码而不是事后手改 best.json：手改会让"算法记录"与"产物"分叉，
下次重跑又退回去。tie-break 让产物可复现。

⚠️ 打平判据用**绝对值容差 1e-9**，不是相对容差；score 本身是 `round(…,6)` 的，
所以相等即完全相等。

## 6. 参数名义值 ≠ 实测值，名义档位里有不可用档

| `outline_px` 参数 | 实测描边 p50 | 可用? |
|---|---|---|
| 2.0 | **1.00** | ❌ 直接违反 `[2,4]` 硬约束 |
| 3.0 | 2.00 | ✅ |
| 3.5 | 2.00 | ✅ |
| 4.0 | 3.00 | ✅ |
| 4.5 | 3.00 | ✅ |

背面剔除吃掉抗锯齿边缘，实测比名义值小 0.5~1.5px（与 `add_outline` 注释里
"8mm→3px、比理论少约 1px"同一现象）。**搜索空间里必须先扫一遍名义值→实测值对照**，
否则"范围 2.0~4.5"里有一档根本不能用，搜索会把预算浪费在必然被 1e6 惩罚的点上。

## 7. rim 与描边争同一批边缘像素（耦合，不是两个独立指标）

受控实测（outline=4.5 固定）：

| `rim_energy` | 描边 p50 | rim 亮带 |
|---|---|---|
| 80 | **4.00** | 9.0 |
| 160 | 3.00 | 9.0 |
| ≥240 | 3.00 | 9.0（饱和） |

两个方向都要报：
- **rim 越强，量到的描边越窄**（4.0→3.0）：rim 把边缘像素抬过 `亮度<40` 的判据。
- **rim ≥160W 后亮带宽度饱和**：toon 三档量化，一旦 Fac 越过 mid 阈值，宽度由几何决定，
  与灯强无关。所以"把 rim 调到 400W"不会让轮廓光更宽，只会把描边削薄。

## 8. 受控对照必须固定其余五维，且要标注"不在搜索预算内"

24 个 Halton 点各维同时变化，按 `outline_px` 分组取中位只是**平均混杂项**，
不能回答"描边宽度 → rim 亮带"。必须另跑定点评估（固定关键维、只变一维）。

本项目另跑了 13 次受控（6 次 outline/rim 梯度 + 7 次 key/skin/azimuth），
在报告里**明确标注它们不在 24 次搜索预算内**，并给出原始日志路径与复现命令。

受控后才发现的两条硬事实：
- `key_energy` 是这套色阶里最敏感的一维：−9W 把 `p95−p50` 从 32 打到 6.2，
  +11W 把皮肤 p50 顶到 228（>215）且 ≥228 占比 50.8%。默认 49W 是可行窗的中间。
- `skin_pos_light` 往高挪 0.08 直接把 `p95−p50` 压到 13.21（硬违规），
  而 `skin_pos_mid` 往低挪 0.04 只让 p50 漂 +0.92。**两维敏感度差一个量级。**

## 9. 并发写入者的处理流程（本项目实测踩到）

现象：开工时 `git status` 干净；跑到一半出现不属于自己的 `M cfg.py / lib/body.py /
lib/head.py`、新文件 `lib/profile.py`，再跑评估直接 `IndentationError`。

处理顺序：
1. **看 mtime 判断是否仍在写**（本项目 20 秒内 mtime 变了两次、大小 17341→17864 → 仍在写）。
2. 等停笔（本项目 2 分钟后 mtime 不动），再 `ast.parse` 逐文件语法检查。
3. 语法恢复后在**最新代码**上复测全部指标 + 上一段探针。本项目五硬指标、rim、裙腰四组数
   **逐位不变**，才敢把那批改动判为"不影响本次结论"。
4. **不能 `git add <项目目录>`** —— 会带上别人的改动；改为逐个精确 add 本次文件。
5. 报告里加「有效性边界」表：11:43 状态（正文数字来源） vs 11:49 之后（含并发改动）逐项对比。

定位语法错误的手法：`eval_pixel` 只打印 Traceback 首末行，`IndentationError: unexpected indent`
不带文件名时，用 `for f in ...: python -c "import ast; ast.parse(open(f).read())"` 逐个文件扫。

## 10. 用 PIL 独立复核正式产物（反证 bottom-up 翻转正确）

`Image.pixels` 的 `[::-1]` 一旦写错，全图分位数看不出问题，但 ROI 会静默上下颠倒。
最省的交叉验证：用 PIL 直接读 `out/` 的正式 PNG，复刻同一套 `edge_dark_width` / `skin_stats`，
与 Blender 内部量测**逐位比对**。本项目两者完全一致（195.02/168.19/227.02/26.82/32.00/4.77，
描边 3.00），这才算证明读图链路正确。

## 11. bash 传 JSON 参数的两个坑

- `--params "{...}"` 里再套一层 `"{{...}}"` 会变成非法 JSON，**失败是静默的**
  （grep 匹配不到 → 日志 0 行 → 看起来像"跑完了没输出"）。函数里用 `--params "$2"`
  不要 `--params "{$2}"`。
- 多组定点评估用 bash 函数循环时，**先 `tee` 到日志再 grep**，否则空日志无法区分
  "没匹配" 与 "真没跑"。

## 12. 交付判定模板（本项目最终写法）

- 五条硬指标：**逐位相同**要写成"逐位"而不是"相近"，并给出 baseline/best 两列。
- 硬指标不变的原因必须解释：本次唯一改动是 `rim_azimuth`，rim 灯在背后，正面机位看不到
  它对皮肤的作用 → 皮肤四项必然逐位相同。
- `skipped_dims` 要区分"预算不够"与"已最优不试"；本项目是前者（第 4 次邻域后预算耗尽）。
- 未完成项要写**为什么**没做（左右不对称未做几何级定位、整圈轮廓光需双 rim 灯超出本次 6 维范围）。
- 回滚给三档：改单个字段 / 删 `pixel` 键 / `git checkout` 后重跑该段搜索器。
