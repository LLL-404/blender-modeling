# 终局重建：产物与源码同源 + 描边壳与探针的相互干扰

适用场景：上游 `lib/*` 已定稿（几何/材质/骨架都改过），但共用产物（`.blend`、姿势图）
还是旧时点生成的。任务是「重跑一次重建入口，让它们与当前代码同一版」，并且**只许改
那个重建入口**（本例 `m5_rig.py`，仅限调用顺序与 import）。

---

## 一、重建入口常见的「漏接」三件套

重建入口是早期写的，只跟上了建模与绑定，没跟上后续阶段新增的渲染件。逐个核对：

1. **材质接线**：后续阶段新增的「把某物体接进主材质表」的调用是否补上
   （例：`look.bind_hands(M)` 把独立建的 `Hands` 从 Principled 占位换成 toon skin）。
   核对法是 grep 同级入口（`m3_look.py`/`m5_outfit.py`）有没有这一行，重建入口没有就补。
   位置放在目标物体 `build()` 之后、描边挂载之前——**描边依赖「outline 材质是最后一个槽位」**，
   材质槽顺序错了 Solidify 壳会指错材质。
2. **灯光参数**：如果后续阶段把三点光收进一个共用函数（如 `shots.stage_c_lights()`），
   重建入口还在手写旧能量值时，出图的色阶整体偏亮（实测 p50 差约 20 灰阶），
   姿势图与其它入口不是一个版本。直接换成共用函数。
3. **描边**：后续阶段加的 Solidify 反法线壳，重建入口往往没有。补上时**必须按每个机位的
   mm/px 换算厚度**（视图恒定像素宽），否则同一个全身机位和特写机位的线宽差数倍。

判断标准不是"能不能跑通"，而是"重跑结果是否与同阶段其它入口同源"。

---

## 二、改完必须重跑，哪怕改动看起来零耦合

改了语句顺序（例如把 `bind_hands` 从 `materials.append` 之后移到之前）也要重跑一次。
理由：交付物的定义是"落盘的 blend/图 与当前源码是同一版"。只要源码变了、产物没重生成，
就回到了任务最初要修的那个病症。重跑成本通常只有十几秒，不值得省。

验证同源性的最简办法：**探针的双模式逐位一致**。
（`factory-startup` 自建场景 vs `-b xxx.blend` 加载已有场景，两模式打印的每个指标
必须一字不差；不一致即说明 blend 与构建路径漂移。）

另外对比同机位像素差这类判据的数值：重跑前后应完全相同（渲染确定性），
若完全相同则证明本次改动没有改变外观。

## 三、描边 Solidify 会让 evaluated 顶点翻倍——把几何探针撑爆

**现象**：带描边的 blend 用探针的「加载已有场景」模式跑，在一个用权重图索引 evaluated
顶点的函数里抛 `IndexError: list index out of range`；同一探针的「自建场景」模式却正常。

**根因**：Solidify 在 depsgraph 求值后每个顶点复制一份（实测 Body 72770 → 145540）。
探针里常见写法 `for i,(a,b) in enumerate(zip(eval_cos, ...)): wmap[i]` 用**原始**顶点
索引去索引**翻倍**后的坐标，越界。自建模式不挂描边，所以不触发。

**定位手法**（不改探针）：一次性 `--python-expr` 打印每个 mesh 的
`len(o.data.vertices)` vs `len(o.evaluated_get(dg).to_mesh().vertices)` 与 modifier 列表。
翻倍 + modifier 里出现 SOLIDIFY，即确认是壳体而非模型错误。
（这一句只做诊断、不落文件，不算"另写一套探针"。）

**解法（推荐）**：存 blend 前把描边 modifier 设成

```python
for m in outline_mods:
    m.show_viewport = False   # viewport depsgraph 不生成壳 → 几何量测干净
    m.show_render  = True     # 渲染 depsgraph 仍生成壳 → 出图仍有描边
```

这样一次满足三方：
- 从 blend 直接 F12 出图**仍有描边**（`show_render=True`）；
- 从构建入口渲染的姿势图**有描边**（渲染发生在改 flag 之前）；
- 几何/权重探针的加载模式**不被壳体污染**（viewport depsgraph 不含壳）。

语义上也更正确：描边是渲染期装饰，不该进入蒙皮几何量测。

**不要**为了迁就探针而干脆不挂描边——那会让 blend 与已交付的姿势图不同源，
正是重建要修的病症。

## 四、既有未达标项的归因

重建之后探针仍可能报几条 FAIL。先判断是不是本次引入的：

- 若该探针的「自建场景」路径**不 import 重建入口**（自己复制建模序列），
  则它测的量与重建入口的改动完全无关；改动前后数值**逐位相同**即为硬证据：
  这批 FAIL 是上游 lib 侧遗留，需另开任务，不能在本入口修。
- 报告里把这类项单独列出并写清 `文件:行` 与成因，不要混进本次交付的达标项里。

---

## 五、交付前的独立确认清单

- 重建**前**记旧 `.blend` 的 mtime 与字节数，重建**后**用 `ls` 再确认（不要只信脚本打印的
  `Saved:` 与它自己的 assert）。
- 每个目标产物都单独 `ls -la`（四张姿势图 + 拼版 + blend）。
- 对象数 / 骨骼数 / 每个变形网格的 ARMATURE modifier 与 parent，用一次性 `--python-expr`
  逐项打印（探针未必覆盖"每个 mesh"）。
- **不要**声称看过渲染图。描边/色阶这类视觉项若没有同机位旧基线可 A/B，就如实写明
  "未做像素 A/B"，只提供几何与配置层面的证据（modifier 存在、厚度换算值、灯能量日志）。
