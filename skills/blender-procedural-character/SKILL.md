# 用 Blender 脚本程序化生成人物

## 何时用

- 用 Python 脚本在 headless Blender 里生成人物（身体、头、头发、服装、骨架），而不是手工雕刻
- 需要改已有建模脚本的几何/材质/渲染，或推进里程碑（素模 → 五官 → 着色 → 头发 → 服装 → 骨架）
- 出现「模型看不了图、还要判断像不像」的情况

## 项目结构与运行

约定：项目目录下 `lib/` 放可复用模块（body / head / hair / outfit / rig / look / shots / meshkit / sheet），根目录放阶段入口 `m1_body.py`、`m2_head.py` ……，产物统一进 `out/`，最终存一份 `*.blend`。

```bash
"D:\Program Files\Blender Foundation\Blender 5.2\blender.exe" -b --factory-startup --python m2_head.py
```

- `--factory-startup` 保证不吃用户配置；`-b` 无头
- 过滤输出只看 `[stats]` / `[render]` / `[done]` / Traceback，避免日志淹没
- 单次渲染约 3–6 秒，可以高频迭代；不要把渲染和改代码塞进同一条长命令

## Blender

> C/D 收口补充（2026-11-01）：`ear()` 局部/世界坐标混用与头宽反向补偿、
> C4 轮廓光在本管线「结构不可达」的完整证据链、rim 判据要先跳过描边、
> 「手 vs 脸」是错误判据（应改「手 vs 同侧前臂」）、正交反投影的两个前提 →
> `references/ear-rim-concha-and-outline-light.md` 5.2 API 坑（实测）

- 合成器：`scene.node_tree` 已不存在。用 `scene.compositing_node_group`（`NodeTree`），没有就 `bpy.data.node_groups.new("Compositing", "CompositorNodeTree")`；输出用 `NodeGroupOutput`，并通过 `ng.interface.new_socket("Image", in_out='OUTPUT', socket_type='NodeSocketColor')` 建接口
- Glare 节点改为输入槽 API：`inputs["Type"].default_value = "Bloom"`（枚举是 `Bloom`，不是 `BLOOM`）、`Quality="High"`、`Threshold`、`Size`（0–1 因子）、`Strength`；旧的 `glare_type/quality/threshold` 属性会抛 AttributeError
- `Shader to RGB` 节点在 EEVEE 下可用，是二次元软色阶的关键；Cycles 不可用
- 自定义法线：`mesh.normals_split_custom_set_from_vertices(list_of_normals)` 可用，配合 `polygon.use_smooth = True`
- 先用 `dir(obj)` / `bl_rna.properties` / 枚举试探脚本确认 API，再写进正式脚本，别照抄旧版本教程
- **`Image.pixels` 是 sRGB 编码值，不是线性值**：实测 Blender 5.2.2 读 8-bit sRGB PNG，像素回读 `0.9765`（=249/255，恰好是皮肤 light 档色），说明它给的就是编码后的 0~1。在 Blender 进程内做像素统计时直接 ×255，**不要再套一次 sRGB 编码公式**，否则整图亮度被抬高约 5%（同一张图 p50 从 229.7 变成 243.5，会误导后续基线对比）
- **`Image.pixels` 还是 bottom-up 存储，PIL 是 top-down**：`buf.reshape(h,w,4)` 的行 0 是图像**最底行**。只做全图分位统计时两种顺序结果相同，看不出问题（A 阶段的探针就因此「看起来逐位一致」）；但一旦有按 `(px, py)` 定位的 ROI 或像素→世界 z 的反投影，整张图会静默上下颠倒——实测同一张 `m3_face_front.png`，鼻下 ROI 中位亮度 168.2（正确）vs 195.9（翻转后），头发高光 in-band 从 97.6% 变成 0%。修法是在 bpy 分支末尾加 `[::-1]`：`... .astype(np.uint8)[::-1]`。**两种读图方式必须用同一张图交叉核对一次具体像素坐标**（不要只比全图分位数），否则这个坑会一直藏着
- **Blender 内置 python 没有 Pillow**（`importlib.util.find_spec('PIL')` 返回 None），Pillow 在系统 python 里。探针要写成「优先 `from PIL import`，ImportError 时用 `bpy.data.images.load` + `pixels.foreach_get` 走同一判据」，并额外用系统 `python -c` 跑一遍 Pillow 核对两边逐位一致，再引用数字。numpy 在 Blender 内置 python 里是有的，直接拿来用
- **numpy 布尔索引在多维数组上极易写错**：`a[:,0]` 取的是第二维第 0 列，不是通道 0；RGB 数组要写 `a[:,:,0]`。这个错在图像统计脚本里会静默地把 mask 形状搞成 `(h,3)`，最后报一个「boolean index did not match indexed array along axis 1」的费解错误
- **界面「工作区」在 headless 下不存在**（`-b` 没有视口），能用的只是它们背后的数据/API。2026-11-03 把 Blender 顶部那 11 个标签逐个实测：

  | 工作区 | headless | 实测依据 |
  |---|---|---|
  | 布局 / 建模 / 脚本 | 能 | 对象变换与选择、编辑模式挤出+细分（f=30）、bmesh 倒角 |
  | UV编辑 | 能 | `uv.smart_project` + `uv.pack_islands` 生出 UVMap |
  | 着色 | 能 | Principled + 贴图节点，`Base Color` 的 `links` 成立 |
  | 渲染 | 能 | EEVEE 出 PNG |
  | 合成 | 能 | `scene.compositing_node_group` 建树成功 |
  | 几何节点 | 能 | 建树 + `NODES` 修改器，求值后顶点数随之变化 |
  | 动画 | 能 | 关键帧写入并求值（第 1/12/24 帧 z = 0 / 0.935 / 2.0） |
  | 雕刻 | **半能** | 能进 `SCULPT` 模式、多级精度能细分（114 → 1922 顶点）；`sculpt.brush_stroke` 报 `poll() failed, context is incorrect` |
  | 纹理绘制 | **半能** | 能直接写 `Image.pixels`；但 `--factory-startup` 下 `bpy.data.brushes` 为 **0 个**（`bapi/sculpt.py` 记的是不带 factory-startup 时只有 1 个 `Draw`），`wm.tool_set_by_brush_type` 返回 `CANCELLED` |

  结论：**手绘笔画这条路走不通，也不要走** —— 笔画不可复现、不能 diff、进不了判据。要用「参数化修改器（位移/多级精度/雕刻遮罩生成的顶点组）+ 直接写像素」替代。
- **Blender 5.2 两处破坏性 API 变更**（实测，写代码前先看）：
  - `bpy.ops.paint.*` 整个命名空间**已不存在**，笔刷改由 `bpy.ops.wm.tool_set_by_brush_type` 管（headless 下无笔刷数据，返回 `CANCELLED`）。
  - `Action.fcurves` **已移除**。改读 `act.layers[0].strips[0].channelbag(act.slots[0]).fcurves`；`act.is_action_layered` 恒为 True。照旧版教程写 `for fc in act.fcurves` 会直接 AttributeError。
- **查参数语义先查手册，别凭记忆**：`python "…/Blender建模/docs/manual_index.py" "实体化 偏移"` 检索离线中文手册（2356 页 / 154 万字，入口登记在 `.agent/tools/blender/index.md`）；`--api SolidifyModifier` 把 API 名直接映射到手册页，`--show <页>` 打全文。分工：`BlenderAPI/catalog/` 给「参数叫什么、默认值多少」，手册给「它什么意思、什么时候用」——两者不可互相替代。手册用词和口语不一致时先看 `docs/手册学习笔记.md` §5 的对照表（「重新网格化」手册写「重构网格」）

## 几何套路（踩过的坑）

- **颈部**：躯干放样直接收成脖子会「颈比下巴宽」。改成独立颈柱（半径约头宽 0.45），后移 `y≈0.02`，靠体素融合长斜方肌
- **发帽**：不要用椭球罩头——椭球在颅顶中段会比头骨窄，露出皮肤。按头骨轮廓表逐环外扩 6mm 再放样；发际线以下的正脸顶点直接塞回头内，边界交给刘海遮
- **脸部法线压平**（原神风）：把前脸法线 lerp 到 `(0,-1,0)` 前，必须给鼻梁/鼻头留保护带（高斯掩码把权重压到 ~0.12），否则鼻子会被彻底压平
- **服装**：衬衫不能只从躯干参数面 offset——身体做过胸部顶点雕塑的话，衬衫必须复用同一个 `sculpt_torso()`，不然胸会顶穿布料
- **裙摆**：按髋半宽 + 净空 2cm 起算，再叠加褶皱振幅；振幅会吃掉净空，要算最内圈
- **耳廓**：椭球压扁后，用「耳轮高斯外推 + 耳甲高斯内凹」变形，并把中心放到头骨表面外（否则整只耳朵埋进头里）
- **贴片五官**：先在平面生成扇面/条带，再沿 +Y 射线投到脸面（BVH ray_cast），最后整体前移 1–3mm 防止 z-fighting
- **鼻子「不可读」多半是着色问题，不是几何太浅**：先量出鼻尖相对额面的实际前伸（按 z 切片取面中线 min y 相减）。有 7–8mm 凸起却看不出鼻子，通常是因为 `flatten_face` 的鼻保护带高斯开得**太宽**（覆盖整个面中）——保护带过宽会保留原始法线、在边缘形成硬明暗线，反而抹掉鼻子。收窄保护带（如 x/0.013→0.008、z/0.016→0.010）比继续加深鼻梁有效；加深过 12mm 就变鹰钩，二次元小鼻不要走这条路
- **表驱动几何的「整体等比缩放」要同时定锚点与远端（头身比是典型）**：只按「绕某锚点 ×k」缩放轮廓表，往往只满足一半验收——缩放会同时把远端（头顶/脚底）推走。实测：绕 z=1.3836 ×1.063 把头长 0.2344→0.2492 做达标了，但头顶也跟着 1.6180→1.6327，把「身高 1.620±5mm」冲爆 7.7mm。正确解法是给缩放**两个自由度**：先用目标头长定 k，再用一个平移把远端钉回目标身高（本例 `shift = 1.620 − (1.3836 + (1.618−1.3836)×1.063) = −12.767mm`，等价于换一个缩放锚点）。连带代价必须写进交付：头整体下移会让脖子露出变短（下巴到锁骨 88.6→76mm）——这是「头长 + 身高」两个死约束的必然结果，不是可以顺手消掉的副作用
- **等比缩放后，所有硬编码的绝对坐标常量都要过同一个映射函数**：面部是重灾区（眼 z、眉 z、嘴 z、鼻的 4 个 z、下巴、颧骨、耳中心，以及法线压平区的 z0/z1 与鼻保护中心）。漏一个就五官相对头骨错位。做法：几何模块里写 `def sz(z): return ANCHOR + (z - ANCHOR) * SCALE + SHIFT`，所有 z 常量用 `sz(...)` 包起来；x/y 方向的半径与中线偏移另写 `sx(v) = v * SCALE`。**着色/压平模块不能 import 几何模块**（会成环），要在自己文件里复制一份同样的常量+函数，并在两处都写「改这里必须同步另一处」；改完用探针量「五官是否还贴在脸上」来验证，别只看代码
- **体素分辨率的硬上限**：`voxel_remesh(0.005)` 会抹掉 <5mm 的特征，之后还有 `smooth` 再收缩一次。手指（宽 6–9mm）、脚趾（8–12mm）在 5mm 体素下必然糊成一坨——「手只有一根圆柱 + 拇指」不是建模偷懒，是融合的物理限制。手/指必须做成**独立物体**（各自 `voxel_remesh(0.002)`），用腕口插入前臂 6–8mm、靠袖口遮挡藏接缝，**绝不能 join 回 Body**（join 后再走大 voxel 会再糊一次）。全局把 voxel 降到 2mm 会让顶点数 ×8，代价与收益不成比例
- **倾斜管件（袖子、发束）的半径不能用水平 z 切片量**：轴线与 z 夹角约 28° 时，水平切片会把垂直于轴的圆环拉成椭圆（长轴 = r/cosθ），而且 18mm 高的 z 带会同时截到好几圈，径向距离被平均中心带偏——实测同一只 60mm 袖口被量成 77.4mm。PCA 主轴同样不可靠：锥形袖筒 62→46mm 的锥度会把主轴拉偏，投影最大端直接抓到肩部；换成「两端质心连线」定轴后，仍要求轴误差 ≲0.006° 才能让整环投影对齐，实际只取到 25/40 个点。**最可靠的是按顶点排列无歧义取环**：`tube()` 的顶点是 `ring0..ringN` 各 `seg` 点，再追加 `cap_start`/`cap_end` 两个圆心，所以末端环就是 `vs[-(seg+2):-2]`；注意 `loft()` 追加的 cap 圆心会让 `顶点数 % seg != 0`（实测 172 = 17×10+2），按 seg 分组前必须先剔掉这两个点，否则环会整体错位。同理，「join 后的大网格里哪一坨是袖子」用**边连通分量**拆——join 只拼接顶点、不做合并，各部件仍是独立壳体（实测 Outfit 拆出 5 块：衬衫 3456 / 两只袖各 1202 / 裙 768 / 领 288），比按 x/z 阈值猜部件稳得多
- **为量测而重建部件时，给生成函数留一个关闭后处理的开关**：`_sleeve(side, solid=False, cuff=False)` 返回未 solidify、未 join 的裸 tube，探针就能按索引取环；默认参数与正式入口完全一致，不改变渲染结果。这比在同一函数里塞调试全局变量干净，也避开了 join 导致的索引重排
- **体素融合后原始顶点索引全部失效，顶点组只能在 remesh 之后重建**：`voxel_remesh` 会重建整张网格，remesh 前记下的索引范围一个都对不上。做法：先记「骨骼折线」列表（每根指/掌给一条 polyline），remesh 完成后遍历顶点，算「点到折线的最短距离」（线段投影要 clamp 到 [0,1]）取最近者归属；再给掌部加一条硬判据（`z > 掌根 z + 4mm` **且** `|y − 掌心 y| < 掌宽/2 + 2mm`）避免掌缘顶点被手指抢走。**只写 z 判据不够**：拇指根比四指根高 29mm，纯 z 判据会把整根拇指判给手掌（实测拇指组从 195 个顶点掉到 38 个）。权重先给 1.0，B 阶段建指骨时再细化；组名带 `_L`/`_R` 后缀，否则两手 join 后同名组会合并、无法分左右
- **「脚陷进地板」只平移脚对象，不要平移 Body**：Body 与 Head 是**独立物体**，把 Body 整体上移 11.6mm 会让颈部与头错位 11.6mm（头骨没动）。正确做法是在把脚 join 回 Body **之前**，对脚对象做 `align_floor(ob)`：量 `min(v.co.z)` 求 dz、只改脚顶点。实测 dz = −1.60mm 就把 `z_min` 从 −11.6mm 修到 +0.000mm，腿/踝/头零位移，腿长比不受影响。**用自动算 dz 而不是手调常量**：几何设计值（脚底 1.5mm）与 remesh 外扩 + smooth 收缩的净值差 1.6mm，手调会让每次改体素尺寸都要重调
- **把部件从 Body 拆成独立物体后，要列一份「它不再享受哪些顺带待遇」清单**：原本 join 在 Body 里、被入口脚本统一处理的东西，一拆出来就全丢了。实测漏了三样：①**材质**——Body 由 `m3/m5` 统一赋 toon，新物体没人赋，渲染时用 Blender 默认白（反照率 0.8），在姿势图里比身体亮一大截，像戴了白手套；②**骨架与权重**——`body.build()` 在 `rig.build_armature()` 之前执行，建模那一刻根本拿不到 armature，所以手在 `wave` 姿势里停在原位；③任何按对象名做的后处理（描边、FOV 拟合、拼版清单）。处理原则：占位要显式（给一个接近皮肤基色的 Principled，并在 docstring 里写「C 阶段必须换成 look 的 skin toon」）、B 阶段要用的顶点组提前建好（带 `_L`/`_R` 后缀，并打印 `[hint]` 组名+顶点数+索引范围）、「未绑定」作为显式缺口写进交付而不是让它悄悄留在图里当瑕疵

## 骨架与蒙皮（踩过的坑）

- **最近骨段权重没有语义**：按欧氏距离取最近骨段，会让「空间上离手近、语义上属于躯干」的顶点被手臂骨抓走。实测百褶裙 z<1.04 的 672 个顶点里 **370 个（55%）** 主导骨是 `hand`/`forearm`——因为裙摆半径 226mm 而手在 x≈232mm，一摆手裙摆就被拽走。修法是**按高度分带限制候选骨**（裙摆只允许 hips/spine/chest），并且**新增 `weight_nearest_banded` 而不是改旧函数签名**（旧函数还有别的调用点）
- **左右串权**：不加 x 符号约束时约 1% 的顶点会被对侧骨影响 >0.1，集中在裆部与腋下（实测 815/66354，z 中位数 0.710）。按 `v.co.x > +0.03` 排除 `.R` 侧骨、`< -0.03` 排除 `.L` 侧骨即可，中轴带留空
- **权重归一性要断言**：所有蒙皮物体的顶点权重和必须 =1（`sum(g.weight for g in v.groups)`），偏差 >0.02 的数量应为 0。这是最便宜的绑定健康检查
- **手写骨 vs Rigify**：参数化身体的关节坐标本来就知道，手写骨架比对齐元骨架更稳；Rigify 只作关节塌陷时的备选
- **姿势存档前先复位**：`save_as_mainfile` 前不 `apply_pose(arm,"rest")` 会把当前姿势写进 blend
- **指骨坐标必须从网格表同源推导，不能和几何各写一份**：每手 13 根骨（palm + 4 指 × proximal/middle/distal）若按毫米数手抄，骨与网格差几毫米就够让手指弯曲时折到指尖外面。做法：几何模块出一个纯计算函数 `joints_for(side)`（同一张 `FINGERS` 表 + 同一套屈曲/张开公式算 4 个关节点），rig 侧直接调它生成 BONES；顺带把 `build()` 里的字面量（根部插入偏移 0.0012 / 0.002）提成常量供两边引用——数值不变，但从此只有一个来源。**新增骨后原 `hand.L/R` 要删掉，凡是硬编码旧骨名的脚本都会 KeyError**（实测 `_probe/rig_probe.py` 读 `pose.bones["hand.L"]` 直接崩），交付时要点明哪个探针作废、新探针在哪
- **改顶点组粒度会静默打断旧探针，要在新探针里把那套判据复现回来**：A 阶段每指 1 组（`index_L`），B 阶段改成 3 段（`index_proximal.L`）后，旧探针的 `g.name.endswith("_L")` 取到空集、`vertex_groups["index_L"]` 直接 KeyError，A 的证据链会断。做法：新探针里用新组名复现同一判据（每指 3 段并起来取最末 5mm 再算连通分量），两个数字一起报；别因为「上一阶段验收过了」就不管
- **给已自带顶点组的物体挂骨架，只加 modifier + 父级，不要用最近骨段权重重算**：`weight_nearest` 会把 13 段手骨揉成软过渡（手指像橡皮），而 Hands 每组权重本来就是 1.0 刚性。写 `attach_weights(ob, arm)`：删已有 ARMATURE modifier → `new('ARMATURE')` + `mod.object = arm` + `ob.parent = arm` + `matrix_parent_inverse = arm.matrix_world.inverted()`。**前提是顶点组名与骨名逐字一致**（Blender 按名字匹配，差一个后缀就不动）
- **分带权重对「整只物体」一刀切会毁掉别处**：裙摆要限制 z<1.05 只允许 hips/spine/chest，但 Body 在同一高度带里有**前臂顶点**（z 0.815~1.045），照抄这条规则会让前臂失去手臂骨、被髋骨主导，一动手臂就散。做法：`weight_nearest_banded(ob, arm, bones, allow=..., side_lock=...)` 传一个按顶点坐标返回候选集的回调——Outfit 是纯 z 分带（z<1.15 → hips/spine/chest，≥1.15 回全骨集合以带动袖口）；Body 是「z<1.05 **且 |x|<0.17**（非手臂区）才去掉手臂骨、但**保留腿骨**」，腿骨不能去否则大腿不跟腿骨。**B1 的指标要量 Outfit 不能量 Body**：Body z<1.04 本就有前臂顶点，「被手臂骨主导」对它们是正确的，混量会把正确的东西算成缺陷
- **侧向约束会「过杀」到 0，这不是越多越好**：`|x|>30mm 排除对侧骨` 一开后 cross_side_leak 从 1.12% 直接到 0.00%（中轴 ±30mm 不约束，否则脊柱/髋会断）。当前四姿势无交叉动作，正确；但若将来加交叉步/抱臂要回头查大腿内侧是否撕裂。交付写「0 是过杀式结果」，别夸成完美。**过杀要主动量化而不是等出事**：写一个**只在临时脚本里**的极端姿势（如 `thigh.L` 绕世界 Y −35°、`thigh.R` −15°，两腿同向交叉；不写回 `POSES`），在**跨切分线**的区域（|x| 20~55mm）量边长比、位移向量夹角、法线翻面，再**在内存里卸掉顶点组重绑一次 `side_lock=False` 做对照**（不写盘）。实测：35°/15° 时 max 边拉伸 4.28×（开）/3.51×（关）；加到 60°/30° 时 **6.25×、17 条边 >5×、21 面法线翻转**，关掉约束只有 5.16×/1/8——即硬切口让应变恶化 22~39%。修法是**把 ±30mm 硬切换成 25~55mm 的 smoothstep 软过渡**（对侧骨权重按 |x| 乘性衰减），并把「交叉 45°/25° 下 max 边比 ≤3、翻面 = 0」写成验收。
- **刚性单骨权重（每顶点 1.0）能把骨架交付做到「骨位正确」，但会让指节变硬折**：B3 只验「骨数 / 组名一一对应 / 权重和 1 / 指尖贴合」，这些在 1.0 刚性下必然成立；真正的形变质量要另造屈指姿势才看得见（实测 `index_proximal.L` −45° + `index_middle.L` −30°：p95 仍 1.000，但 70 条边 >1.5×、max 36×、6 条 <0.6×，其中 36× 来自 0.1mm 级短边被放大，统计时要先滤掉 <0.1mm 的 rest 边）。若下游要做手指动画，必须在关节 6mm 内做 2 骨线性混合（如 distal/middle 交界 0.7/0.3），并把 A1/B3 的「边长比」验收换成屈指姿势下的口径。
- **分带的允许集比要求更严时，要把额外严格度的代价量出来**：B1 只要求「手臂骨不主导」，实现却是「z<1.15 只允许 hips/spine/chest」——于是裙摆腿骨权重为 0，`walk` 下裙摆平均位移只有 5.40mm、腿 89.26mm（**6.05%**，裙 hem 仅 1.8%），且 49 个腿/臀顶点越出裙面最深 14.83mm（rest 只 4 个）。判「达标 + 代价」并给可执行修法：`z<0.78` 允许 `thigh.L/R` ≤0.35（按 x 符号 + 中轴混合）、0.78~0.95 线性回收，验收加「裙 hem 位移 ≥ 腿位移 20%」，并把这套左右混合的串权指标扩展到 Outfit（B2 原来只量 Body）。
- **「组数对」不等于「组名对」**：验收每手 13 组时不能只数 `len(vgroups) >= 13`。要三件一起报：①`set(组名) == set(该侧骨名)`（missing / extra 都列出来，差一个后缀 Blender 就不驱动）；②每组实际吃到的顶点数（实测 distal 38~62、proximal 106~154、palm 1761），空组等于骨没绑上；③**无任何组的顶点数 = 0**（没组的顶点在姿势下不动，会被误读成"蒙皮坏了"）。骨数也要给算式核对：45 = 5 躯干/头 + 6 臂 + 26 手 + 8 腿，26 = 2 palm + 24 指骨。
- **半更新的探针比没更新的更危险**：改骨名/组名后常有人只改了探针前半段（例如腕部台阶那节），后半段仍用旧组名——脚本会先打出一串漂亮的数，再在 `vertex_groups["index_R"]` 上 KeyError，看着像"新出现了问题"其实只是没改完。回归时逐个跑探针并记录 `Traceback 行号 + KeyError 的键名`，明确报"失效 N 个"；不要沿用上游"只有 1 个失效"的说法（实测 2 个：`a1_hand_probe.py` 与 `_probe/rig_probe.py`，后者崩在 `pose.bones["hand.L"]`）。
- **绑定序列抽成一个函数，别让入口脚本和量测探针各写一份**：Body 分带 → Outfit 分带 → Head/Hair 刚性 → Hands 挂骨架，两处各写一份必然漂移，探针的结论就不再对入口有效。抽成 `rig.bind_all(body, cloth, head, hair, hands, arm, side_lock=)`，入口与探针都调它。**探针做成双模式**：场景里已有 `Rig` 就直接量（`blender -b 美女.blend --python probe.py`，顺带验证存盘/重开无损），无则按入口同一序列自建；两份结果应逐位一致，不一致说明 blend 丢东西。**pose 差异率擦线要当缺陷报**：B4 断言「两两 ≥15%」，实测 `rest vs walk = 15.09%` 只高 0.09 个百分点，这种项要单独标出并写明「材质一改就可能跌破」，不要只写 PASS

## 验收：看不了图怎么办

现成模板：`scripts/geometry_probe.py`（通用几何量测探针，含 bbox / z 切片 / 膨胀连通分量 / 面中线前伸 / 净空穿模 / 权重归一 / 姿势驱动）。拷进项目 `_probe/` 直接用，别再重写一遍、重踩下面这些指标错误。

另附 `scripts/pixel_probe.py`：**双模式**像素统计（Blender 内无 Pillow 时走 `bpy.data.images`，与系统 python + Pillow 逐位一致），含描边扫描线宽度、皮肤三档最近邻分位、正对机位的世界↔像素 ROI、rim 亮带（会先跳过描边暗带）。它把下面第 13 条与本文件「C 阶段」的全部判据都实现了一遍——改一处配置（OUT / VIEWS / SKIN_TIERS）就能在新项目里跑。

1. **几何量测**：按 z 切片打印各高度的 x/y 范围（宽、深），对照头身比、肩髋腰比例、颈宽
2. **像素统计**：用 Pillow 统计渲染图的主色占比、皮肤亮度分位（5/50/95%）。皮肤亮度全挤在 240 附近说明色阶是平的；头顶区域 skin 占比高说明发帽被头骨顶穿。一套实测可用的皮肤判据（sRGB 0~255）：`r≥180 且 g≥160 且 b≥140 且 r≥g 且 g≥b−10`——能排掉深色背景（≈53,59,74）、地板（≈97）、头发最亮档（≈174,158,166）、虹膜（≈247,178,77），只把眼白算进来（<1% 面积）；用它的结果与旧基线（202.0/229.7/230.0）只差 3，可直接对比。**这套判据还能验构图**：逐行统计皮肤像素，第一条/最后一条有皮肤的行就是头顶/身体边界——首行上方留白过小或该行占比异常高，就说明头被画面裁了，是「模型放大后忘记把相机 target 跟着改」的可靠探测法（看不到图也能判）
3. **区域分类**：按颜色把「皮肤 / 头发 / 高光 / 背景」分开统计各 ROI，比整体直方图更能定位穿模
4. `analyzeImage` 视觉评审只作旁证：它会给具体但可能失真的描述（例如把几何上存在的耳朵说成没建）。结论要注明是间接证据，**绝不要声称自己看过图**
5. 该视觉服务会返回空结果（`EMPTY_OUTPUT_FALLBACK`）。失败两次就换路径，不要再堆同一调用。**这通常是暂时不可用，不是永久故障**（实测同一轮里先连续空结果、十几分钟后恢复），交付里别写成"工具坏了"；恢复后可再用一次，但仍只作旁证
6. **点云连通分量**：判断「有没有分叉」（手指、脚趾、发束）时，把 z 切片投到 (x,y) 平面栅格化再数连通分量。两个必踩的坑：①**不能按 x 排序看间隙**——闭合环在 x 方向天然断成两段，单根圆柱会误报 5–8 段；②**必须对每个点做 r=3mm 膨胀**——体素重网格后顶点间距约 5mm，裸 2mm 栅格会把一张连续面切成 17–103 块假阳性。膨胀后单管正确归为 1 个分量，5 指才报 ≥4。③**膨胀半径会反过来约束几何尺寸**：验收写 `xy_components ≥4` 时，相邻指尖中心距必须 **> 半径和 + 2×dilate**，r=3mm 就是「+6mm」；再给 remesh 外扩（每侧约 1mm）留余量，实际要 ≥16.5mm。指根间距只有 11.75mm（掌宽 42mm / 4 指）时**光靠掌宽做不到**，只能给每根手指一个张开角把指尖扇开（实测 −15°/−2°/+10°/+30°，指尖中心距 17.5/17.1/16.1mm）。先按这个公式算一遍再动手，别做完发现分叉数不够
7. **切片带的高度也是口径，不写清楚会让短指整根漏掉**：手指有了张开角，z 投影按 `cos(spread)` 缩短（30° → 20mm 指长只剩 17.3mm），短指指尖会比中指高约 10mm。用「z ∈ [手 z_min, +10mm]」的窄带会漏掉小指，实测报 3 而不是 4，看着像融合、其实是没切到。改成 12mm 带即达标（真人也如此：中指尖与小指尖高度差 10–15mm）。**并同时给一个不依赖带高的交叉验证口径**——用顶点组取「每根手指组内最末 5mm」的点再合并求连通分量，两个数字一起报
8. **脚趾的连通分量有一个「解剖上必然连通」的固有陷阱**：脚掌与脚趾在 xy 投影上必须连在一起，所以按 DESIGN 原文的裸 z 切片（如 z∈[8,20]mm）**上限就是 1 个分量**，加了脚趾也改变不了。要判「脚趾有没有分开」必须加 y 限制取趾区（脚掌前端做到 −92mm，就取 `y ≤ −96mm`）。交付时同时打印「趾区口径」与「裸切片对照值」，并写明前者才是判定依据，否则验收方会按裸口径判 FAIL。**这个 y 分界是前后方向常数，不要乘 side**：`c.y * side <= TOE_ZONE * side` 在 side=−1 时会把对侧脚掌后半部全选进来（实测报 1 分量、点数 1211 vs 正确的 139），左右不对称且极难一眼看出来
9. **膨胀用的栅格精度要够**：1mm 栅格在「间隙只剩 1.5mm 余量」时会被整数取整吃掉、误判粘连。用 0.5mm 栅格 + 精确圆盘判据（`dx²+dy² ≤ r²`）比放大间隙更省事。numpy 实现膨胀时**必须留 pad = r+2 的边缘**，否则 `np.roll` 的循环卷绕会把远端内容接到有效区域上
10. **正交投影下「直径不压缩、中心距压缩」，机位角度决定分叉可见度**：圆柱/球的屏幕投影宽度恒等于直径，而两指中心距按 `right·Δ` 压缩（`right = cross(view, up)`）。所以从正前方（view≈(0,1,0)）看，手指张开只体现在深度、屏幕上完全重叠；视线 x 分量越大指缝越宽。实测同一双手：view x=0.58 时指缝只有 1.6mm（看不清）、x=0.72 时 3.0mm（可辨）。代价是视线越偏侧，同侧大腿越容易挤进正交视野（只脏背景、不穿模）。**先按这个公式选机位，别靠试**：指缝宽度 ≈ `Δy × |right_y| − 指直径`
11. **指标定义先定口径，否则同一数据得相反结论**：「眼距」按瞳孔间距/眼全宽算得 1.95（结论"过宽要改"），按内眼角间距/眼全宽算得 0.95（结论"标准不要动"）。美术语义上的眼距通常指内眼角间距。写指标时必须写明「分子取自哪两个点、分母是哪条边」。同类坑实测还有两个：①**「鼻尖相对额面前伸」的额面窗口**——基线探针的额面取 z 1.520~1.570；若误用 1.470~1.520，窗口里含着鼻梁最高推量点，额面基准被提前约 6mm，前伸会从 7.70mm 掉到 4.85mm，看上去像「改完反而更浅」，差点据此又去加深鼻子。**引用任何旧基线数字前，先回到旧探针把它的窗口/阈值原样抄下来**，别凭「大概是这段」重写。②**法线压平验收的区域**——「面中 |x|<13mm 法线偏离 −Y ≤25°」如果把下巴也圈进去（z 下限放到下巴高度），会在下颌转折面量到 28° 直接判超标，而面中鼻唇区只有 17.8°。z 窗口必须写进口径，交付时同时报主口径与参考口径，并说明后者为何不作为判定
12. **「姿势到底有没有驱动网格」要单独验**，别只看图：读 `arm.matrix_world @ pose.bones[x].tail` 的世界坐标、比较 evaluated mesh 的 bbox 在 rest/wave/walk 下是否变化、再看多张图两两像素差异率（>12% 才算真的不同）
13. **toon 色阶是平的，先查光照分布再改色值**：`最终色 = base × ramp`，三档色值本身常常合格（相邻档线性亮度差 ≥15% 即可）。真正的病是 95% 像素落在 light 档——判据：皮肤亮度 p95−p50 ≥30、p50−p5 ≥25；实测出现 p50=229.7、p95=230.0（只差 0.3）时，该动的是 ColorRamp 的 `pos` 与灯强，不是换颜色
14. **符号约定写进注释**：正面朝 −Y 时「y 越小越靠前」，净空 = `body_y − shirt_y`（>0 才是安全）。这类符号写反会让脚本把「安全」报成「穿模」，而且很难自检
15. **`solidify(offset=0)` 会让同一处净空出现 4mm 的口径差**：厚度 4mm 居中时，外表面比原始环层前 2mm、内表面后退 2mm。「身体 vs 衬衫」的净空因此有三个数——环层口径（最小，也等于真正的设计 grow）、外表面口径（比环层大 2mm，`min y` 取到的就是它）、内表面口径（比环层小 2mm，才是真实最近间隙）。实测同一份改动：断言（solidify 前采样环层）14.3/15.0/15.0mm，探针（最终网格 min y）15.7/16.0/14.7mm。**报数字必须写明是哪一层**，否则和旧基线比会凭空多出 2mm，把刚达标读成「很宽松」。做法固定为：内联断言在 solidify 之前采样，探针量最终网格，两边各自标注口径
16. **上游给的「基准半径」可能取自另一个剖面位置**：`body.arm()` 的 `rs` 表里 45mm 是 z=1.220 处的参数半径，而袖口实际落在 z=1.110，该处只有 38.8mm（Body 实测，同轴同面的中位数）。拿 45mm 去减，会把 8.2mm 算成 2.0mm、把 14.2mm 算成 7.2mm，结论完全翻转。**任何「部件半径 − 上臂/大腿半径」的差值，两个半径必须同轴、同剖面**（垂直于同一轴线、过同一平面）；引用上游数字前先确认它对应哪个 z
17. **不达标要诚实写进交付**：基线跑通 ≠ 达标。把它拆成「运行结果」（退出码/耗时/产物）与「质量结论」（量测缺陷清单）两段，避免"跑通了"被读成"做好了"
18. **渲染图上「分叉到底可不可见」用横向扫描线 run-length 判，别靠感觉**：在指/趾区取几行，按亮度阈值（如 >60）切亮段，亮段宽度应 ≈ 部件直径、段间暗缝 = 真实间隙的投影。实测同一双手部近景：亮段 45/46/46px（=8.0/8.2/8.2mm，对上指宽），缝 17px（=3.0mm）→ 能数出 3 根同层手指；换到更偏正面的机位后缝只剩 9px（=1.6mm）就分不出来。这个数字同时验证「几何上真有分叉」与「分叉在最终图上真的可辨」，比一句「看着还行」可靠得多
19. **把渲染图压成字符亮度网格，是「看不到图」时最便宜的形貌旁证**：按 56×72 分块求平均亮度、映射到 ` .:-=+*#%@` 打印，就能从文本读出「腕—掌—4 指」的层次与各段比例（本案例掌宽 42mm 折合 21 个字符，与理论 42/1.96 吻合；手指只出现在画面下部 11 行 ≈ 27mm，与指长 26–28mm 吻合）。这属于可复现的像素统计、不是目视，可以写进交付；但结论要标注「由亮度网格推得」，不要写成「我看了图」
20. **包围盒达标可能靠附属部件撑起，必须写表注并绑定复测**：头宽验收取 `Head` 对象 bbox 得 0.2139（达标），但 `HEAD` 表本体只有 0.2062——达标完全来自两只耳的外缘。这类「间接达标」有三类风险：①改附属部件（耳内收、呆毛变细、袖口放宽）会**静默掉达标**；②bbox 含对称件时，单侧尺寸错误会被另一侧掩盖；③深/高同理。做法：凡是 bbox 口径的指标，同时报「本体值」（不含附属件的表/网格极值），并在表格里写表注「达标来源 = X，改 X 必须复测」，别只留一个 ✅

## 独立复核（挑刺式验收）

接到「几个生成者都自称达标，你来挑刺」这类任务时，**生成者的自述一律不算证据**，按自己的口径重算一遍，结论必须落成「指标 / 阈值 / 实测 / 判定」四列。

- **脚本组织**：一个 Blender 进程内的几何脚本（按入口 `m*.py` 的真实顺序构建：`M=look.set_all()` → head → `flatten_face` → body → hair → outfit，**不要按 `import` 依赖顺序乱建**，否则参数面与网格面对不上），外加一个纯 Pillow 的像素脚本。每条量测打印 `[acc] key=value` / `[px] key=value` 并同时写 JSON，报告才能逐条回溯；不要让一个脚本既建模又解析 PNG（Blender 内置 python 没有 PIL）。
- **JSON 落盘前先清洗 numpy 标量**：`np.float64` / `np.bool_` / `np.int64` 都不是 JSON 可序列化的，`json.dump` 会在**最后一步**抛 `TypeError`，前面几十条量测全白跑（本轮踩了两次）。写一个递归 `_san()`：dict/list 递归、`np.ndarray→tolist`、`np.generic→item`。**收尾写盘要抗中途失败**：验收脚本越到后面越容易炸（实测最后两节才用到却没 `import cfg` → `NameError`），一炸整轮只剩 stdout。做法是边量边 `REC[key]=val`，收尾 `try/finally` 落盘，或每节结束写一次快照。
- **别用 bash heredoc 往长脚本里插大段 Python**：三引号内容一旦和 heredoc 终止符/长度纠缠，就可能只写进去一半甚至完全不写（实测 python 报 `unterminated triple-quoted string`，文件其实没动，命令却继续往下跑）。改用 `write` 落一个片段文件、再 `head + tail` 拼接；改完先 `grep -c` 行数 + 命中目标锚点，确认真的写进去了再跑。
- **单字母全局对象名会被循环变量悄悄覆盖**：长脚本里习惯写 `b = body.build()`、`h = head.build()`，若下面遍历里写 `for a, b in zip(nz, nz[1:])`，Body 对象就变成 int，几十行后才在 `me = ob.data` 炸出 `AttributeError: 'int' object has no attribute 'data'`，栈里看不出根因。全局物体用 `body/hair/cloth/hands` 全名，循环变量一律带后缀（`ia/ib`、`na/nb`）。
- **「姿势有没有驱动某个物体」用 depsgraph 的 evaluated bbox 判，不要用两张图的像素差**：`m5_rig` 的四张姿势图**每个姿势换一台相机**（rest 2.3/−2.5/1.0、wave 1.2/−3.2/1.15），跨图相减的差异率里混着整个机位变化（实测全图 37%），没有归因力。正确做法：按 `m5_rig` 的方式绑 Body/Outfit/Head/Hair（**故意不绑 Hands**），`apply_pose` 前后各取 `evaluated_get(dg).to_mesh()` 的 bbox——实测 Hands Δ=0.000mm、Body Δ=283.9mm，一句话定案；再核 `obj.modifiers` 与顶点组名是否含骨名（Hands 12 组全是 `palm/index/…`、无 `hand.L` → 未绑）。
- **run-length 数手指必须限定 ROI 并去碎片**：整幅阈值化会把画面边缘的大腿/墙亮块也算进来（实测数出 5–6 段）。三步：①阈值取在背景 p50 与部件主峰之间（实测背景 50、手 172–218，取 150；Otsu 会被右侧亮背景拉偏）②列方向只保留「含图像中心、且该列前景像素 ≥30」的连续区间③每行 run 宽 ≥6px，相邻 run 暗缝 ≤4px 合并（否则高光把一根手指劈成两段）。
- **报告数字和你复算差 1~2mm 时，先把几种已知口径都算一遍再下结论**：本轮「衬衫净空 15.7/16.0/14.7」与 `[fit]` 的 14.3/15.0/15.0 差 1~2mm，原因是前者=身体网格 vs 衬衫外表面、后者=参数面 vs solidify 前环层；按身体网格口径复算后**逐位复现**，说明不是换口径、更不是造假。若同一改动在任何口径下都对不上，才判「不可复现」。
- **采样容差本身就是口径**：同一个裙腰净空，`|x−0.040|≤12mm` 量出 −2.0mm，收紧到 `≤6mm` 量出 −5.6mm（穿透集中在 x 28~66mm 的乳下侧）。报「最差值」必须同时报采样范围，否则会把缺陷说轻。
- **判定分四档，别把三种完全不同的情况混成「未达标」**：`达标` / `未达标`（真缺陷）/ `口径存疑`（数字成立但判据脆弱）/ `合理偏离`（偏离字面值但有独立证据）。两个典型对照必须分开写，否则会派错活：①**生成者的判据自我合规**——把「指尖带 10mm」改成 12mm 才凑到 4 分量，且 4 分量只存在于 4mm 薄带、余量 1.2mm；几何分叉是真的，但判据脆弱 → 判「口径存疑」，建议换成不依赖带高的「每指自身末 5mm」②**上游字面指标本身错误**——DESIGN 的「裸 z 切片 ≥2」在脚趾上解剖必然连通，加多少趾都改不了，换「y 扫过趾根」的口径才对 → 判「达标 + 口径存疑(上游)」，不要打回生成者。
- **给「偏离」写两段式判定（数值是否成立 / 理由是否成立）**：偏离者常给两条理由，可能一对一错。实测「袖口 53mm 会切进上臂」是错的（53>47 只会更松；同轴同面算 53−38.8=14.2mm 是超上界、不是穿模），但「超出 [7,10]」成立 → 结论「合理偏离，理由需更正」：不否定数值，也不放过错误论证。
- **跨图差异类判据先做「同机位对照重渲」再判读**：如果四张测试图**各自换机位**（实测相机两两夹角 7.1°~29.2°），两两像素差里混的是视差，不是姿势。做法：自建场景按入口同一序列绑定后，**只用一台相机**把全部姿势渲到验收子目录（如 `_stageB/tmp/`，绝不覆盖 `out/` 里的共享产物），再按同一算法算差。实测同一批姿势：换机位口径 14.98~37.96%、同机位口径只有 4.24~15.54%（仅 1 对 ≥15%）——最低那一对（rest vs walk 14.98%）恰好是机位最接近的一对，说明「擦线通过」是机位差凑出来的。结论要写成「判据度量的是机位变化」，修法是统一机位 + 重定阈值，或直接换成几何判据（每姿势相对 rest 的 p95 顶点位移）。
- **测试区域先自检「真的有几何、真的跨过要测的机制边界」**：任务里给的区域常常是空的或没覆盖机制。实测两例：①「大腿内侧 |x|<30mm、z 0.70~0.80、y ±0.05」这条区域整体落在侧向约束的**豁免带内**，所以 side_lock 开/关给出逐位相同的数（等于没测）；②把 z 带放在胯部融合段时，|x| 30~45mm 的表面只出现在 |y|≈0.06 之外，y ±0.05 里**一条边都没有**（n_edges=0）。规则：每个区域都打印 `n_edges / n_faces`，为 0 就换区域；要验「硬切口的过杀」必须让区域**跨过切分线**（如 |x| 20~55mm）并覆盖真实有面的前/后表面。
- **指标若在 rest 与 pose 下给出逐位相同的数，它就是「姿势无关」的，不能当质量证据**：手部单骨 1.0 刚性权重下，`wave` 的手指边长比恒为 1.000、指尖到骨 tail 的 min/max 与 rest 完全相同（差 0.00mm）——这两个指标只能验骨位，验不了蒙皮。自检办法：同一指标在 rest 与 pose 各算一次，数值相同就换个**真会改变该部位几何**的临时姿势（如屈指 45°/30°）再测；实测一换姿势就暴露 70 条边 >1.5×、max 36×。
- **「内外 / 穿模 / 到表面距离」类判据要有物理先验，先让 rest 接近 0 再信姿势下的数**：本轮两种写法都翻过车——①用「最近点法线点积」判内外，遇到 solidify 双壁（内壁法线朝内）会把 15,236/15,404 个顶点判成「在裙外」；②区域没排除手臂，`max_poke` 直接报到 114mm。改成「按 (z, 角度) 分桶取裙面半径、比较身体顶点同角度半径」的径向法后，rest 降到 4/5585（≤0.86mm，与已知的裙腰微穿模量级一致），walk 才是有意义的 49/6037（最深 14.83mm）。规则：rest 下报出成千上万个「越界」时先怀疑测试，不要拿去写缺陷。
- **约束本身即指标时，0% 只说明约束生效，不说明风险消失**：`side_lock` 让 cross_side_leak = 0.0000%（|x|>30mm 的对侧权重最大值也正好 0.0）——这是构造出来的恒等式。必须同时报**豁免带内的最大对侧权重**（实测 0.467，>0.10 的顶点 4288 个）与「关掉约束会怎样」，并说清 0 是设计使然而非质量提升。
- **多人在同一项目并行时，复核方只写自己的量测脚本**：不碰 `lib/*.py`、`m*.py`、`cfg.py`、`DESIGN.md`，发现问题靠报告打回；量测产生的临时日志/JSON 落在项目内的验收子目录（如 `_stageA/logs/`），不要写到工作区根。

## 方案文档回填（设计稿 → 实测事实）

下游把 DESIGN.md 执行完之后，文档里的"基线"会集体过时。回填不是改几个数字，而是**把两个时点的数据对齐**，否则会把已修好的缺陷又写回去。

- **先辨识快照时点，再动笔**：同一项目里同名指标常有多个时点值。实测验收方 `accept_geom.json`（07:16）是**打回时**的快照——裙腰 −1.43/−2.03/−2.15mm、首次 4 分量 12mm；而返工（07:25/07:27）后的真值是 +3.5/+7.4/+3.0/+10.8mm、14mm。直接采信 JSON，会把**已经修好的穿模**写回文档，制造一个不存在的缺陷。做法：`ls -l --time-style` 看每个产物的时间戳，和任务单里的返工时间比对，确认"哪个文件早于哪次返工"。
- **冲突时以任务给定值为准，但两个时点都要落盘**：盘上快照 73,228v / 12mm vs 任务给的 72,770v / 14mm，两者都对，只是时点不同。文档写「返工后 72,770（07:25）」，附录保留「打回时 73,228（07:16）」作为历史，**不要二选一**。对"任务给了但盘上无快照"的值（如袖口 47mm、14mm 深），显式标注「任务汇总值，盘上无对应快照」。
- **文档开头加显式时点声明**：一句话写清「基线有两个时点，别混用」，并逐节列出哪节用哪版。否则读者会拿 §1.2 的新值去比 §5.2 的旧日志，然后得出"文档自相矛盾"。
- **回填前抽样核对键名，不要凭印象填**：新基线有十几项，先在 JSON 里逐个命中（`head_len` / `nose_protrusion_mm` / `mouth_over_head_bbox` / `ear_height_mm` / `shirt_margin_body_*` / `cuff_R`…），确认数值和口径都对得上，再写。对不上的单独列出来。
- **区分「过时」与「历史对照」**：改完 `grep` 旧值（7.51 / 0.2344 / 6.95 / 14.8% / 60mm / 10.3 / 13 个对象）。命中在「A 前 / 历史 / 口径对照」句子里的是**应该保留**的锚点；命中在「实测值 / 当前」列才是漏改。**不要无差别全文替换**。
- **表格加「来源键」列比加「说明」列有用**：每行指回 `accept_geom.json` 的键名，后续有人质疑数字能一键回去核对，也自然暴露"这一项根本没有量测来源"。
- **加列时优先「实测结果」而不是「备注」**：任务表后面直接加一列 `A 阶段实测结果`（✅ + 值），再另起一小节列「打回 / 返工记录 N 条」。这样"计划 → 实际"的偏离一眼可见，不用埋进长段落里翻。
- **大表整块替换比逐行 patch 稳**：表头 + 分隔行 + 全部数据行一起换，避免加列后列数不一致（7 列 vs 6 列会渲染错乱）。
- **markdown 单元格里的 `|` 必须先转义**：写 `|x|` 会让表格错列，也会让后续 `edit` 的 oldString 匹配失败（实测原文未转义、匹配串写成 `\|x\|`，整块替换直接报"找不到"）。要么写「x 的绝对值」，要么用 `\|`；遇到这种失败不要重试同一串，改成只替换表头 + 首行的最小片段。
- **未达标项要显式标注优先级，不要含糊成「部分达标」**：回填后剩 10 项未闭环，用 ✅ / ⏳ 两列状态 + 「低优先（改它会连锁躯干表/裙长/腿骨）」标签，比一句"大部分已达标"可执行得多。
- **体量要有上限意识**：本次 42 KB → 70 KB（466 → 684 行）。每加一节先问"能不能合并进已有条目"；口径陷阱已在正文 3 条 + 新章 7 条时，就在标题写「另外 N 条见 §X」做交叉引用，别再全文重复一遍。

## C 阶段：三渲二质感（描边 / 面部阴影层 / 色阶 / 头发高光）

顺序固定 **描边 → 面部阴影层 + 部件接进 toon → 头发高光 → 色阶重标定最后**。色阶会改所有图的亮度，前面按「亮度<40」「皮肤 p50−20」定的判据全部漂移，必须最后做并全套复测。

### 描边（Solidify 反法线外壳）
- **`offset` 必须是 +1，不是 −1**：offset=−1 让壳朝内长、被本体完全挡住，球体扫描线实测暗带 **0px**；+1 才有轮廓线。
- **`use_flip_normals=True` 必须配材质 `use_backface_culling=True` 一起用**。flip 单独用（不剔除）会让外壳正面遮挡本体 → 整个对象变黑（实测中心亮度 194→39）。
- **描边色要够黑**：线性 0.02 经 Standard 编码是 sRGB≈41，正好卡在「亮度<40」判据上方，实测判据恒为 0。取线性 0.005（≈15）。
- **线宽按视图换算，不要固定米数**：同一 thickness 在 560×900/ortho1.78（1.98mm/px）上是 3px，在 620×780/ortho0.30（0.385mm/px）的脸部特写上变成 **20px 粗黑框**。做法 `thickness = px_target × ortho_scale / res_y`，每个机位渲染前重设 Solidify 厚度。球体标定：2.08mm/px 下 5mm→1px、8mm→3px、10mm→4px（比理论少约 1px，背面剔除吃掉抗锯齿边缘）。
- **多材质槽对象靠 `material_offset` 指到新加的 outline 槽**（Head 有 9 个槽 → offset=9）；`use_rim=False`；壳生成后顶点数应为原网格 2 倍（可自检）。
- **join 过的对象会把贴片五官一起套壳**：Head 含眼睛/眉/唇贴片，Solidify 会给它们各加一圈黑边（脸部内部暗像素 95→542）。这可能是可接受的「眼线」也可能是脏边——没有看图能力时如实报数字与风险，别声称「看起来正常」。
- **验收用扫描线 run-length，不用目视**：逐行找前景左右边界（背景色取四角中位），在边界 ±8px 窗内量「亮度<40」的最长连续带，取 p50。目标 2~4px。

### 面部阴影层（材质节点，不动几何）
- 纯 `Geometry.Position` 盒判据：`z > sz(1.38) 且 y < -0.02` 命中脸区，给 ColorRamp 的 Fac 加偏移。
- **符号方向别写反**：ramp 的 light 在 pos[2]，**Fac 越大越亮**。设计稿写「+0.15 让脸更早进 shadow」在数学上是反的，实测 −0.15 才让 shadow 档占比 9.1%→11.8%。
- **只靠全局偏移往往跨不过档位**：整脸均匀偏移时 p50 与 ROI 一起移，差值不变（实测鼻下 ROI 仍 229.7）。鼻底那道 3~5mm 硬阴影带要单独给一段更小的盒（z 3~5mm、`|x|<12mm`）+ 更强偏置（−0.6），才能把 ROI 压到 168。
- 头骨被重锚过（缩放+平移）时，**所有 z 阈值必须过同一个 `sz()`**，包括着色侧自己复制的那份。

### 头发高光（天使环 band）
- MapRange `0.95→1.66` ⇒ `p = (z−0.95)/0.71`；验收「p99 像素的 z∈[1.52,1.60]」对应 p ∈ [0.803, 0.915]。
- **只上移上面那道带会崩**：p99 的最亮像素主要来自**下面那道带**（0.585 → z 1.365）。实测把上带从 0.845 移到 0.905，in-band 从 63.7% **暴跌到 3.66%**。正确做法是**把两道带都放进验收 z 区间**（[0.803,0.845] 与 [0.858,0.915]），实测 97.6%。

### 色阶重标定（先算数，别盲调）
- **动手前先算三档跨度**：显示亮度由 `base × ramp` 固定，皮肤三档实测 **182.2 / 208.5 / 227.7（跨度 45.5）**；而「p95−p50 ≥30」且「p50−p5 ≥25」相加要求总跨度 **≥55**。**只调 pos 与灯强无论如何达不到**（p50 会被 mid 档 208 钉住、p95 最多 227）。先判断这一点，再决定是否允许动色值，否则会盲目迭代七八轮。
- 允许动色值时的最小改法：加深 shadow、把 mid 拉离 shadow（如 shadow (0.50,0.47,0.64)→(0.485,0.455,0.625)、mid (0.86,0.74,0.76)→(0.752,0.647,0.664)），保持「档间线性亮度差 ≥15%」的配色规范；再把 pos 收到 (0.0, 0.62, 0.68) 让 light 档占到 ~9%。实测四项一次达标：p50 195.0、p95−p50 33.7、p50−p5 26.8、≥228 占比 5.5%。
- **调 pos 时盯 light 档占比**：p95 只有 light ≥5% 时才会到 227；light <2% 时 p95 落在 mid→light 过渡区（215~221），分位差怎么调都差 10 以上。
- **灯参数集中到一处**：m3/m4/m5 各自硬编码 `key 70W` 会让改灯时漏改入口。抽成 `shots.stage_c_lights()` + 模块常量，三个入口都调它。

### 轮廓光（rim）的结构性限制
- 在「rim 在人物正后方 + 3px 黑描边占住轮廓最外缘 + 白衬衫/皮肤已达 light 档 227」的组合下，**正面/侧面机位量不到 2~6px 亮带**：轮廓边缘是掠射面，受光后亮度仍 ≤ 主体（剖面实测边缘 130~200 vs 内部 195~249）。提到 80W、size 0.8、甚至把灯移到侧后做受控实验，仍是 0px。
- 结论写成「指标在当前布光下结构不可得 + 三条原因 + 建议（rim 移到侧后并对深色区域验收，或改背面机位）」；不要为凑数放宽判据（跳过描边暗带的判据修正是必要的，继续放宽就是作弊）。

### C 阶段纪律
- **改共享材质/灯之前先把参数常量化**，否则「一次只改一项」在三个入口上会漂。
- **色阶之后全套复测**，包括描边宽度与面部 ROI（它们都依赖亮度阈值）。
- **测「手与脸肤色差」先分清材质 vs 光照**：材质统一后手的全部像素都落在同一 skin 三档内，剩余亮度差由 key 单侧布光造成（实测背光侧 14.8、受光侧 0.1）。判据用「最近档色距离」而不是绝对亮度，才能把「材质没接对」与「背光」区分开。
- **C 阶段之后，用另一套材质/灯的入口（如 `m5_rig.py`）的四姿势图必须重渲一次**，并在该入口补上「新部件接进 toon」的那一行调用，否则它的产物会和其余 C 阶段图色阶不一致。

## 子进程拼版坑

用 PowerShell + System.Drawing 拼图时，`subprocess.run(..., text=True)` 会因中文路径/GBK 输出抛 `UnicodeDecodeError`，随后 `r.stdout` 为 None 再崩。改为 `capture_output=True`（bytes），再用 `utf-8` → `gbk` → `replace` 依次解码。

## 工作流纪律

- 渲染命令被拒，不要原样重试第二、三次；第一次就停下说明状态、给原因清单并追问。**执行通道可能被锁到连 `blender --version` 这种秒回命令也被拒**——不要用小命令"探门"，也不要把命令换个壳（`cmd /c`、PowerShell）再撞；直接转「代码落盘 + 完整命令交给用户」
- **同一项目可能有并行的团队会话**：`<workspace>/.codeartsdoer/agent-team/session/<id>/team-task.json` 里有 content / target_files / status / owner，能看到别人正在改哪些文件；改公共文件前先读，避免覆盖。实测 `人物建模` 已被另一会话推进出 `DESIGN.md`、`lib/hand.py`、`_stageA/` 等产物
- 用户选「先写代码」后：把脚本改完落盘，结尾附上完整可执行命令，并明确写「改动已落盘、尚未渲染验证」
- 一次只改一类问题（几何 / 材质 / 服装），改完立刻渲染并用统计量核对，别攒一堆改动再一次跑
- **新特效的参数组合先在最小场景里扫描，再落到正式对象**：描边这类有「offset 符号 × flip_normals × backface_culling × thickness」四维组合，在 240×240 的单球场景里一次跑 5 组只要几秒，能直接讲清「哪组根本不出线」「厚度与像素宽是不是线性」；直接在全身场景试会浪费 5~10 倍时间，而且结论里混着轮廓形状的干扰。扫描结果要写进代码注释（本项目的 `add_outline()` docstring 里就记了 0px/1px/3px/4px 的对应关系），别只留在会话里
- **改之前先算一遍判据是否可达**：遇到「分位差 ≥A 且 ≤B」这类成对阈值，先用可测量的色档/几何跨度算一算有没有解（例如三档显示亮度跨度 45.5 而两个分位差相加要求 55，就无解）。算不过就直接改设计参数并写清理由，比盲调七八轮省得多
- **上游给的「现状判断」先用一次运行证伪，再采信**：被交代「某阶段还没跑通 / 某处可能穿模」时，先跑一遍拿退出码 + 产物 + 量测，再决定要修什么。实测出现过相反结论——被判定"骨架尚未跑通"的入口脚本其实退出码 0、10 秒、4 张姿势图 + 拼版 + blend 全部正常，只是**从未被运行过**。基于错误前提写方案，会去修一个不存在的问题
- **多路并行改完后，验收第一步是把全部入口重跑一遍**（`m1_body`…`m5_outfit` + `m5_rig`），只过滤 `[stats] [render] [fit] [rig] [done] Traceback Error`，核对退出码与每个物体的顶点数/对象数，再进入逐项量测。组合回归抓到的往往不是各模块自身的问题，而是「各自都对、拼起来坏」的三类：`body.build()` 里新加的 Hands、`outfit._sleeve()` 新增的关键字参数、`head` 的整表缩放与 `look.flatten_face` 的 z 区间没同步。跑之前先读入口结尾 20 行确认有没有 save/render 副作用
- **先验基线，再写方案**：改代码前把当前状态量成数字（比例、分数、净空、色阶分位），方案里每个"目标值"都要有对应的"实测值"和"容差"。没有实测值的方案无法验收，也无法判断改动是否有效
- **阶段顺序按依赖排，不按难度排**：几何 → 骨架 → 材质 → 细节。先做几何是因为材质验收的像素指标会在每次几何改动后全部漂移，先做材质等于白测；先做骨架是因为手部改造后指骨权重才可能加
- 验收脚本放在项目内子目录（如 `_probe/`），注明用途并声明「不参与建模、不被任何 m*.py 引用」；临时文件不要写到工作区根目录
- **偏离上游给的参数时，把「为什么」和「代价」都写进交付**：上游常常只给一个数（例如「绕锚点 ×1.063」）。实算下来它只满足部分验收时，可以加第二个自由度（平移），但总结里必须给出推导算式、指出是哪条验收逼出了它、以及连带视觉变化（脖子变短 / 五官相对偏移）。不要悄悄改，也不要为了守字面就交一个超差的结果
- **撞见越界范围的既存 bug：记录，不顺手修**：改某个部件的尺寸时，很容易在同一函数里发现别的 bug（实测 `ear()` 把物体**局部**坐标与物体**世界**位置相减，导致耳轮/耳甲的高斯恒为 0，耳朵一直是个光椭球）。这属于「一次只改一类」的边界——写进函数 docstring 和交付清单、交给下一阶段，不要同一轮顺手改，否则所有改动无法归因
- **上游参数与验收阈值互斥时，先算穿模边界再决定**：实测「袖口半径 53mm」与「袖口 − 上臂 ∈[7,10]mm」在真实几何下互斥——53−38.8=14.2 超出上界；而若保留原末端点、只把半径降到 53mm，袖口内壁会切进上臂 6.3mm，因为袖口中心比手臂轴外撇了 21mm（这也是旧 60mm 的由来：它刚好是"外挂式包住手臂"的最小半径，内侧余隙只有 ~1mm）。处理步骤：①先用算式定位是哪个约束逼出了偏差（本例是「末端点不贴手臂轴」），②选一个满足**可实测**阈值的方案（贴回轴 + 47mm → 8.2mm，区间中部，留 1.2mm 抗扰动余量；46mm 只有 7.2mm，贴下界），③交付里同时给出两种口径的数字、被放弃的字面值、以及「要守字面值」的等价代价（本例：把袖长缩到 z≈1.20，53−45.9=7.1mm 能同时满足两者，代价是中袖变短袖，属造型决策不擅自做）。**不要为了守字面数交一个穿模的结果，也不要悄悄改而不说明**
- **同批次多人在改同一项目时，探针要做依赖隔离**：探针只 import 自己需要的模块（body/outfit/hair）并自带材质 stub，**不 import 正在被并行修改的 `look.py`**，否则对方中途的语法错误会把整条量测拖挂。反过来，`hair.py` 顶部 `from head import HEAD` 是硬依赖，对方把 `head.py` 改到一半（实测第 238 行 `IndentationError`）会让探针 `import hair` 直接失败——按纪律等 30 秒重试一次，恢复即继续；**仍失败只记录现象，不越界去改对方的文件**
- **多人并行改同一项目时，用文件时间戳证明自己没越界**：交付前列 `ls -la --time-style=+%H:%M` 核对「我改的文件」与「别人改的文件」，把这条当「未触碰公共文件」的证据；若上游文件在同批里被改过（例如脚底已被别人抬到 z=0），自己的量测必须重跑，不能引用旧结论
- **跑「只为验证没崩」的回归前，先查这个入口有没有写盘副作用**：`m5_rig.py` 结尾会 `save_as_mainfile("美女.blend")` 并重写全部 `m5_pose_*.png`。只想确认「我的改动有没有破坏骨架入口」时直接跑它，实际会覆盖上游产物——实测就因此违反了「不要写 `美女.blend`」的硬约束，只能在交付里如实报告「该文件已被重写为当前代码的正确新状态」。做法：先读入口末尾 20 行确认有没有 save/render；只要「不崩」的证据时改走 `--python-expr` 只 import + build（不 save、不 render），或在副本目录里跑
- **交付里主动报「我越界做了什么」，别等对方发现**：本轮明明只被授权改 4 个文件，却因为跑回归把 `美女.blend`、`m5_pose_*.png` 一起重写了；同时 `Body` 顶点数从 66,354 涨到 73,228（脚单独走 3mm 网格的必然结果，不是 bug）。这类副作用与数字变化要单独列一节「副作用」，写清「内容是什么、为什么、能否恢复、下游该改哪份文档的哪个数字」，不要混进「已完成」里
